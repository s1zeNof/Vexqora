# Vexqora — SVG Pixel Drone для AI-чату

Codex, інтегруй підготовлену серію анімацій Vexqora в **існуючий AI-чат проєкту**. Ми вже узгодили дизайн дрона: це фірмовий зелений піксельний дрон із двома чорними очима, бічними пропелерами, мікропікселями, диханням і зависанням. **Не перемальовуй SVG і не створюй PNG/GIF/відео.** Використовуй додані готові SVG-файли та підлаштуй інтеграцію під реальну архітектуру репозиторію.

## Готові assets

Розмісти у прийнятній для проєкту директорії статичних ресурсів (для Vite це може бути `public/animations/vexqora/`, але спочатку перевір фактичну структуру):

| Файл | Призначення | Тривалість |
| --- | --- | --- |
| `vexqora-logo-static.svg` | Початковий і фінальний стан | Статичний |
| `vexqora-logo-to-drone.svg` | Логотип → пікселі → дрон | **2800 мс**, 1 програвання |
| `vexqora-drone-thinking-loop.svg` | Дрон дихає, кліпає, парить, обертаються пропелери, рухаються пікселі | **2400 мс/цикл**, нескінченний loop |
| `vexqora-drone-to-logo.svg` | Дрон → пікселі → логотип | **2200 мс**, 1 програвання |
| `vexqora-drone-static.svg` | Статичний дрон для reduced motion | Статичний |

Усі файли — **реальні автономні SVG** з прозорим фоном. Файли візуально узгоджені: start закінчується дроном, idle починається дроном, reverse починається дроном і закінчується справжнім логотипом Vexqora. Вхід/вихід не повинні повторюватися самостійно; повторюється лише `thinking-loop`.

## Основна логіка

Реалізуй як окремий компонент/хук станів, інтегрований з фактичним життєвим циклом запиту чату.

Стани:
- `idle`: статичний логотип;
- `entering`: SVG logo-to-drone, одне програвання 2800 мс;
- `thinking`: SVG drone-thinking-loop, повторюється **стільки часу, скільки потрібно**;
- `exiting`: SVG drone-to-logo, одне програвання 2200 мс;
- `idle/revealed`: статичний логотип, і лише тоді показати відповідь або помилку.

**При відправленні повідомлення:**
1. Одразу додай повідомлення користувача до чату.
2. **Одразу запусти існуючий API-запит до ШІ** (не чекай завершення анімації, не затримуй мережевий запит).
3. В області майбутньої відповіді покажи анімований логотип (`entering`) замість типових `typing dots`/спінера.
4. По завершенню 2800 мс, якщо AI ще генерує — переключи на нескінченний `thinking`. Якщо відповідь уже отримана — відразу переходь до `exiting` (не додавай штучних 3 секунд idle).
5. Поки AI генерує, утримуй дрона в `thinking` незалежно від кількості циклів. Не запускай повернення в логотип через фіксований таймер.
6. **Коли AI повністю завершив відповідь**, збережи результат у буфері, переключи з `thinking` у `exiting`. Якщо AI завершився під час `entering`, дочекайся завершення цього етапу.
7. Відтвори reverse SVG повністю **2200 мс**. **Тільки після нього** додай/відкрий фінальну відповідь у чаті, заміни анімацію статичним логотипом, прибери стан pending і віднови звичайний UX.
8. Так само обробляй неуспішний запит: після reverse коректно покажи повідомлення про помилку (якщо проєкт уже має error UI — використай його).

**Ключове правило:** відповідь AI НЕ може з'явитися в UI до завершення `exiting`. Буферизація стосується відображення: мережа/бекенд відповідають без затримки, UI акуратно чекає закінчення SVG.

## Streaming

Перевір, чи використовує чат SSE, fetch stream, WebSocket або інший спосіб потокового отримання даних. Якщо так, накопичуй chunks у локальному буфері (або ізольованому draft, який не рендериться у чаті) до фінального `done` / завершення stream. Не показуй ні проміжні tokens, ні markdown, ні partially streamed content користувачу під час `entering/thinking/exiting`. Після reverse відобрази остаточний текст. Збережи існуючу логіку Markdown, посилань, форматування й persistence/history.

У разі синхронної відповіді або дуже швидкого API (`< 2800 мс`) **не перескакуй** animation-in: завершити `entering`, потім програти `exiting`, потім показати відповідь. Для повільних відповідей `thinking` може обертатися 10, 30 або 60+ секунд без артефактів.

## Технічні вимоги

- Спершу знайди існуючий компонент чату, `sendMessage`/submit-handler, API-client, streaming/rendering code, місце для assistant placeholder, стикування з історією й обробкою помилок. **Не створюй паралельний чат і не замінюй API.**
- Зроби явно визначений state machine, наприклад `idle → entering → thinking → exiting → revealed`, із незалежним прапорцем `responseReady` / buffered response.
- Для `<img src="*.svg">` внутрішні SVG/SMIL `endEvent` не доступні через звичайний DOM елемент image. Тому для зміни фаз використовуй синхронізовані константи `ENTER_MS=2800` та `EXIT_MS=2200` і коректно прибирай timers, **або** вбудовуй SVG inline і слухай реальні SMIL `endEvent`; обери мінімально інвазивний надійний спосіб. Не покладайся на `onAnimationEnd` зовнішнього `<img>` — він не спрацьовує на внутрішній SMIL-анімації SVG.
- Під час зміни фази перемонтовуй `<img>` (`key` від `requestId` + `phase`) для гарантованого старту SVG з нульового кадру. Попередньо завантаж SVG-файли, щоб не було flash або порожніх кадрів.
- Контейнер усіх фаз повинен мати **однакові width/height/aspect ratio** без зсувів повідомлень. SVG viewBox у всіх 5 файлах однаковий.
- Передбач cleanup таймерів, abort/stop, помилки, розмонтування компонента, повторне надсилання, stale-response/race conditions і незалежність кожного запиту. Не дозволяй старій відповіді завершити анімацію/показати текст для нового запиту.
- Якщо чат підтримує декілька одночасних генерацій, прив'язуй стан до **конкретного messageId / requestId**, а не до одного глобального boolean `isLoading`. Якщо підтримує лише одну генерацію, збережи існуюче блокування.
- У разі `prefers-reduced-motion: reduce` використовуй статичний дрон під час запиту і статичний логотип після, без зайвого очікування 2.8/2.2 с.
- Якщо вкладка прихована й браузер призупиняє анімації, не видавай UI за завершений перед користувачем, який повернувся; синхронізуй фази при поверненні вкладки, щоб не було обриву reverse.
- Під час очікування оголошуй доступний screen-reader статус (наприклад, `ШІ готує відповідь`), не дублюй зайвих анонсів кожні 2.4 с.
- Не змінюй анімації в решті інтерфейсу без необхідності. Не чіпай бекенд, не підробляй інтервал API, не втрачай швидкість генерації — затримка лише в момент розкриття відповіді.

## Перевірка / acceptance criteria

1. Звичайний сценарій: відправлення → морфінг до дрона → безперервний `thinking` → морфінг назад → відповідь.
2. Швидкий API (100–500 мс): вхід завершується, потім вихід, потім відповідь. Без flash статику/дрона між фазами.
3. Повільний API (15–30 сек): дрон залишається живим необмежено, не зникає і не повертається в логотип сам.
4. Streaming: нуль видимих токенів до завершення reverse, потім коректна повна відповідь, історія збережена.
5. Помилка/abort/retry: чистий перехід, немає завислих thinking-спінерів і старих таймерів.
6. Reduced motion: статичні стани без зайвої затримки.
7. Мобільна/десктопна версії: однакові розміри контейнера та цілісна геометрія логотипа.

Після реалізації покажи: які файли проєкту змінив, де лежать 5 SVG, схему станів і як перевірив ці сценарії. Не зупиняйся на описі плану — **реально інтегруй це в кодову базу Vexqora**.
